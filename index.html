Your site

Turn your site into a desktop app

Pier reads the web app manifest you already ship and builds a real desktop app around your site: its own window, its own menus, a Dock icon, and the files, ports and devices a browser will not hand over.

Your manifest, key by key

name, icons

The app takes its name and icon from the manifest. A square PWA icon is fitted to the system’s icon tile; one with its own shape is left alone.

{
  "name": "Phonotheque",
  "id": "/app",
  "icons": [{ "src": "/icon-512.png", "sizes": "512x512" }]
}

display, scope

Tabs, the address bar and someone else’s buttons go away. Your page runs the same code it always did, now inside a window of its own. A link outside the scope opens in the browser.

{
  "display": "standalone",
  "start_url": "/app",
  "scope": "/app"
}

epwa.permissions

Declare what your site needs. Pier shows the list in the install dialog and bakes it into the app; anything you did not declare answers with an error, even when your code asks for it.

{
  "epwa": {
    "permissions": ["files", "midi"]
  }
}
DeclareAnd your page can
nothing Drive the window and titlebar, fill the menu bar and the Dock menu, register global shortcuts, keep running in the background, store secrets in the Keychain, ask for Touch ID
files Open and save through system panels, then read, write, watch and trash what the person picked — across launches, without ever seeing a path
network Fetch without CORS, open TCP, TLS and UDP sockets, browse Bonjour, accept incoming connections (loopback unless the person allows more)
serial usb hid bluetooth midi Talk to the device the person picked in the system chooser. Keyboards, pointers and security keys are never handed over
notifications Post native notifications with buttons, a reply field and attachments, and hear about every click
camera microphone location screen Ask the operating system. It prompts, it decides, and Pier cannot work around the answer

144 methods and 50 events in total. The full reference is docs/bridge-api.md, generated from the same spec the runtime is tested against.

One button on your page

The helper is a single file, no build step. It hides itself where Pier cannot run, and hands the app whatever state the visitor had in the tab.

import { canInstallApp, launchApp } from './pier-launch.js';

button.hidden = !canInstallApp();
button.onclick = () => launchApp({
  manifest: '/manifest.webmanifest',
  handoff: { track: player.currentTrack },
  onLaunched: () => player.pause(),
});

The click opens

epwa://launch?manifest=…&handoff=…

Pier fetches the manifest over https, shows the person what the site is and what it asks for, builds the app, and opens it on the track they were playing. Already installed? It just opens.

Lint a manifest before you publish it: web-runtime check <url>.

What the app cannot do

  • The bridge answers the main frame of your own origin. An ad iframe, a login popup and any other site get an error.
  • Files, ports and devices arrive only through a system chooser. The page never browses the disk.
  • Leaving your scope opens the browser and closes the devices and connections the previous page held.
  • These limits are checked by tests on every build, not promised in prose.

Install it and see

You ship a manifest, not a binary: no developer account, no certificate, no notarization, no yearly fee. The app is built and signed on the person’s own machine, so it opens without warnings — and Pier needs no admin rights to do any of it.

Removing an app is removing an app: drag it to the Trash, and Pier clears what the site left behind on its next launch.
